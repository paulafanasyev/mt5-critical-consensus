## New findings

### Blockers

**B1 — The registered cluster floor and the code disagree (24 vs 30), and the code applies the development floor to the holdout.** §7 says "100 development trades and 30 clusters" (L230); the operative decision rule says `clusters ≥ 24` twice (§8.2 L243, §8.4 L252); the code sets `MIN_CLUSTERS = 30` (L50) and uses it for both windows (L544-547). A 26-cluster development sample is judged under §8.2 but is `no_decision` in the code; a 26-cluster holdout is refused and the one permitted look is burned, although §8.4 says judge it. Since §8.6 (L257-259) forbids re-parameterising after step 1, this must be reconciled before the run — either change the document to 30, or add a separate `MIN_HOLDOUT_CLUSTERS = 24` and use it at L544. As written, the study cannot be run as registered.

**B2 — The double-cost floor is not part of the holdout pass, and `verdict` makes it optional.** §6 says "the decision uses the base cost and additionally requires the edge to survive at double cost" and "a result that lives inside the uncertainty of the cost model cannot pass" (L209-211). The holdout pass in §8.4 has no double-cost condition (L252-254), `verdict` passes when `double_cost_mean is None` (L548), and `main` computes the sweep on the holdout only if `--cost-sweep` is passed (L595). Concrete: dev double-cost +0.03 R, holdout base +0.15 R but double −0.01 R → the code returns `pass`, and the study reports an edge that is inside the cost model's uncertainty. Fix: compute the sweep on both windows and require `double_cost_mean > 0` for any `pass`; do not let `None` mean "skip the floor".

**B3 — The holdout gate is a speed bump, and §8.3's enforcement claim is false.** `open_holdout` accepts any JSON with `window == "dev"` and `decision.passed == true` (L493-510); `test_a_holdout_cannot_be_opened_without_a_passed_development_run` fabricates exactly that four-line file and opens the holdout (tests L537-543). The lock stores the sha256 of that file (L505-507), so fabrication *before* the first open is invisible. The lock is plain JSON (L509) and deleting the candidate key re-opens it. `require_holdout_open` is called only from `build` (L515-516), so `simulate` + `summarise` score the holdout with no lock. The lock contains no engine hash, so `rule_c1`/`max_hold` can be edited after development and the holdout still opens. §8.3's "deleting the document is the only way around it, and that deletion is visible" (L249-251) is false: editing the evidence and editing the lock are silent. A burned holdout can therefore be presented as clean. Fix: store an engine hash and the full evidence schema (n, clusters, low, confidence, seed, manifest), require the lock in `summarise`/`simulate` or make the holdout a closed function, and correct the claim.

**B4 — §2's audit still overclaims, and the §12 timeline is incomplete.** §2 says "No artefact in this repository has examined a pre-2020 daily price path for any trading rule" (L27-30), while §1 admits the engine and test suite were exercised over 2004-2019 (L7-11); the suite calls `simulate`/`rule_c1` on the dev window (tests L405-412, L451-489), and `agent_data/_patch_tests7.py` L4-5 records the then-independent C1 implementation being edited from `index < 2` to `index < 30` to match the engine. The true claim is "no artefact records or displays a result". The §12 table says the suite ran at "15:20-15:22" (L313), but `.pytest_cache/v/cache/nodeids` is stamped **15:37:18**, after the engine's last edit (15:37:03) — a post-fix collection or run that §12 omits. §12 also says "15:40 This revision" (L316) although the document's mtime is 15:37:15; §11 says "36 tests" (L291) although the file collects 37; and §2 calls `docs/DEMO_RESULTS.md` "about one year" (L41) although its 540 H1 cycles are about one month (`docs/DEMO_RESULTS.md` L32). The audit is substantially better than round 1, but the "record is complete" claim is not true.

**B5 — The "three independent implementations" are not independent for the C1 exit/re-entry logic, the warm-up test is vacuous, and no test pins the bootstrap interval's width.** `_fill` (tests L75-96) is a verbatim transcription of `protective_exit` (engine L145-165): same branch order, same `stop_gap`/`target_gap`/`stop`/`target` labels. `_independent_c1` (tests L120-139) copies the engine's `while`, the `min(deadline-1,last)` protection bound and the `index = hit[0] + 1` re-entry. A shared misreading of the prose — protecting `E+1..E+H`, or resuming at `exit+2` — would pass parity. The `assert rule["intent"][:30] == [0] * 30` (tests L375) is vacuous: `_walk([100.0] * 40)` cannot signal before index 30 (every close is 100, inside the previous bar's 99-101 range), so an engine with `WARMUP_C1 = 2` would pass. All four bootstrap tests are degenerate — all-positive, all-negative, net-zero clusters, and `block=12` over 12 clusters (tests L495-526) — so an implementation returning `[mean, mean]` would pass every one; the interval width, which is what `low > 0` turns on, is never tested. Fix: rewrite `_fill`/`_independent_c1` from the prose with a different structure, add a signal at index 20 to the warm-up test, add a re-entry-positive test and a time-exit-precedence test, and add a bootstrap width test with known non-zero variance.

### Majors

**M1 — The boundary tests pin the exit date but not the two decisions that can move the trade list.** `test_the_time_exit_lands_on_the_registered_bar` (L277-289) does not test a bar `E+H` that opens inside both levels and later trades through the target: the engine exits at the open (correct per §5), but nothing pins that the time exit pre-empts the intrabar touch. `test_no_signal_is_taken_on_the_bar_a_position_closes` (L291-302) does not test that a signal on `exit+1` is taken; `test_simulate_never_overlaps_two_positions` (L305-312) would pass if the engine skipped two bars. A shared off-by-one here changes the trade count, and every subsequent entry and R, and the suite would not notice.

**M2 — An underpowered holdout is recorded as `fail`, not "inconclusive".** §8 promises that a holdout failure below the ≈0.36 R detection threshold is "inconclusive, not disconfirmation, and the verdict text will say so" (L261-264). `verdict` returns `status: "fail"` for any straddling interval once `n ≥ 30` and `clusters ≥ 30` (L554-563); the only `no_decision` is a sample floor (L540-547). The removed test `test_verdict_refuses_to_call_an_underpowered_sample_a_pass` (still in `.pytest_cache/v/cache/nodeids`) shows the distinction was dropped. Concrete: a real 0.20 R edge with a holdout mean of 0.08 R and interval [−0.28, 0.44] is written to the evidence as `fail`, and a later reader sees "did not survive out of sample", exactly what §8 says must not be recorded.

**M3 — Development is not run-once-locked.** `main --window dev --json` overwrites `DEV_EVIDENCE` on every run (L610-612); the evidence carries no run counter, no code hash and no lock. §8.1's "Run development once" (L241) is unenforced. Re-running development with variants until one passes is invisible, and it raises the study-level false-pass rate from the registered joint ≈0.04% (0.83% × 5%) to the holdout's one-sided 5%. The holdout gate protects the holdout, not the development stage.

**M4 — The block bootstrap is coarser than the document implies.** The clusters are months **with at least one trade** (`keys = sorted(clusters)`, L375-394), so "three consecutive months" can be three clusters years apart; the wrap-around at L391 joins 2019-12 to 2004-06. At the 30-cluster floor the 0.83% tail is estimated from about ten blocks, so the nominal family-wise 2.5% is optimistic there. `test_the_block_bootstrap_draws_consecutive_months` (L509-515) uses `block=12` over 12 clusters, which proves block *size*, not contiguity.

**M5 — The double-cost gate does not bind for C1.** From §6's formula, `cost_r ≈ (0.20 + 0.0022·price)/(2·ATR)`, roughly 0.10-0.13 R on gold over 2004-2019 (order of magnitude; I did not run the data). The 98.33% lower bound at 100-180 clusters requires a net ≈0.21-0.29 R, i.e. a gross ≈0.31-0.40 R, while the double-cost floor requires a gross of only ≈0.20-0.26 R. The economic floor is real in principle but is dominated by the interval for C1; it only binds above roughly 500-800 clusters.

**M6 — The direction split is diagnostic, not a decision criterion.** `by_direction` is reported (L446-451, L606-607) and §5 warns that a long-only pass is a drift result (L136-138), but the pass rule (§9 L273-275) does not require the short side to contribute or even to have a minimum count. A gold long-only drift can pass and be reported as a compression result, with the caveat buried in a diagnostic field.

**M7 — The end-of-window trade is a mark, not an exit, and counts in `n`.** The last dev trade is closed at the 2019-12-31 close (L306-307) and included in `n` and the mean; at `n ≈ 100` one such partial trade can move the mean by ~0.01-0.02 R. The report gives the `end` count in `reasons`, but the prereg does not say whether the mean should be read with or without it.

## Residual risk if run as written

- **A `pass` can be a long-only gold drift.** The direction split is reported but not gated (M6), and §5's warning is not a decision rule.
- **A holdout pass can rest on an edge inside the cost model's uncertainty.** The double-cost floor is not applied to the holdout and is optional in `verdict` (B2); a candidate can be reported as robust when its holdout mean is ≤0 at double cost.
- **A real edge of 0.2-0.3 R will usually be recorded as `fail`, not "inconclusive".** The holdout at ~30 clusters has ~50% power at 0.36 R and much less below it; the code has no "inconclusive" status (M2), so the expected outcome for a modest true edge is a false negative presented as disconfirmation.
- **The 0.83% is nominal at the 30-cluster floor.** A 98.33% percentile interval from ~10 blocks is not calibrated to 0.83%, so the family-wise 2.5% is optimistic exactly where the sample is thinnest (M4).
- **The one-shot holdout is only as good as the operator.** Development can be re-run, the evidence can be fabricated, the lock can be edited, and the engine can be changed after development; none of these is detected (B3, M3).
- **The 2020-2023 buffer is read backwards at the 2024-01-01 edge.** This is disclosed in general but not for C1's 30-bar/ATR read (round-1 #5).
- **Small-sample sensitivity to gaps and the end-of-window mark.** Favorable gap fills can produce R > 2 and adverse gaps R < −1 (the prose intentionally fills at the open), and the final dev trade is a mark included in `n` (M7); at `n ≈ 100` either can move the mean by a few hundredths of an R.
- **The study is a weak test of a real edge, by construction.** A true 0.30 R edge passes the joint gate perhaps a third of the time; a true 0.21 R edge less than a fifth. That is a legitimate design choice ("powered for large edges only"), but it should not be read as evidence that a smaller edge is absent.
