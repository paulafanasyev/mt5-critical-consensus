## Stop new commands

The persisted kill switch defaults to active. To activate it from the Windows bridge host, configure MT5_BRIDGE_TOKEN in the process environment and run:

    ./scripts/activate_kill_switch.ps1 -Reason "Stop new MT5 demo commands for investigation"

The script requires a successful persisted confirmation. Verify the current server state via authenticated GET /v1/risk/kill-switch. If the API/DB is unavailable, the EA fails closed and will not poll for commands.

The demo-only loopback bridge answers the same POST, so the same command stops the demo path: it flips a durable `kill_switch.json` beside its tombstones, which the advisor polls and the demo runner reads before every queue. A runner already inside a cycle therefore blocks at its next command, and a stop armed this way survives a restart of either process. While no runner is alive, lift it with `python scripts/run_mt5_demo_trading.py --policy … --db … --tombstones … --release-kill-switch` after exporting `MT5_KILL_SWITCH_ADMIN_TOKEN` (≥32 characters, different from the bridge token); `--policy` and `--db` are required for every invocation of that script, including this one. The same second secret is required on the API path, in `X-Kill-Switch-Admin`. Both sides re-read the file on every check, so a release made in one process is obeyed by a running bridge or runner without a restart. Deleting `kill_switch.json` is not a way to disarm anything: a record that existed and then vanished is answered 503 (which the advisor treats as blocked), and a path with no record at all is served as armed (`NOT_SEEDED`). A first runner that finds no record seeds one as armed too, with reason `SEEDED_ARMED` — it deliberately does **not** read `kill_switch` from the policy, because a policy file describes how to trade and is not a permission to trade — and it never overwrites a record an operator or a halted run left behind. An interrupt that lands after a command was served is its own arming event: the run marks the command unconfirmed, arms this record and exits `4` (`interrupted_with_send_in_flight`).

The EA itself checks the persisted kill-switch endpoint on every timer tick and again immediately before `OrderSend`; if the state is unavailable or active it aborts. Demo execution is gated by the compile-time `const bool ENABLE_DEMO_EXECUTION = false`, which must remain false during compilation and smoke tests, and AllowLiveExecution must remain false. Remove the EA from the chart / disable Algo Trading while investigating. The endpoint and EA stop new command polling; **they do not cancel an already submitted broker order or close an open position**. A human must inspect MT5 Journal, Orders, Deals and Positions and reconcile any uncertain OrderSend result before taking further action.

## Revert software

- **Before merge:** delete the local `harden/10of10` branch or add a corrective commit to it. No production rollback is required because the work is isolated from `main` and has not been pushed.
- **After a future reviewed merge:** use GitHub's Revert action for the merge commit or create a dedicated revert PR. Do not force-push main or rewrite the audit history.
- **After a future deployment:** keep the kill switch active, roll the deployed API/worker/EA package back to the exact previously verified release, compare its commit hash, and rerun health/contract tests before considering reactivation. No hosting/preview deployment is configured for this repository, so only a recorded local or CI run for the exact commit counts as release evidence.
- **Database changes:** migrations are forward/idempotent and market, risk and resolved-forecast evidence is intentionally immutable. Do not delete audit evidence to roll back code. If a migration requires correction, add a new forward migration reviewed against a backup and test database.

## Reactivation criteria

The switch may only be disabled with the separate `MT5_KILL_SWITCH_ADMIN_TOKEN` of at least 32 characters: on the API path it travels in `X-Kill-Switch-Admin` alongside the authenticated request, and on the demo path `--release-kill-switch` takes it from the environment (the command line carries no header, so there the environment value is both the configured secret and the proof it was offered). Do not reactivate while any risk snapshot is missing/stale, market/news calendar evidence is unknown, provider roles or calibrations are unproven, there is an unresolved broker result, or the build/test state is red. In this scaffold, unknown news status deliberately keeps risk-controlled permission denied.
